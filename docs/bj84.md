# Smart Switch Air (BJ84)

## Product and channel behavior

The tested BJ84 panels were identified by their owner as LifeSmart's
[Smart Switch Air](https://iot.ilifesmart.com/product/Smart-Switch-Air/).
The official product page describes four lighting circuits and eight configurable
keys for lighting and scene control. Its terminal specification lists four load
outputs (`L out 1 2 3 4`), plus `L in` and `N`.

The owner reports four load-control switches that can also be configured as
logical switches, plus four logical switches. This configuration detail comes
from the owner; the product page does not document relay decoupling or assign
physical outputs and logical functions to specific API ports.

The eight Home Assistant switch entities therefore represent the panel's
reported API channels, not eight physical relay outputs. Their effects depend
on the panel's existing configuration. A logical channel can participate in a
configured scene or automation without directly switching a load.

## Integration behavior

`SL_SW_BJ84` creates a switch for each reported `P1` through `P8` channel and
preserves its name. Local discovery normalizes `SL_SW_BJ84_V1` to this model.
Updates for all eight ports follow the existing switch state dispatcher. Device
and hub exclusions continue to apply. Other switch models keep their existing
port selection.

All reported channels use the existing on/off switch interface. The integration
does not assign relay or scene roles by port number, change the panel's
configuration, or add button, curtain, pulse, or automatic-reset behavior.

## Protocol references and limits

The reviewed copy of LifeSmart's [official development documentation](https://ilifesmart.com/open/#/open/document/developmentGuidance)
is **Device Specification Attributes v2.32**, last revised
2024-08-15 (download listing updated 2025-07-28). Section 2.2 documents switch
state as the parity of `type`, with on parameters `type=0x81, val=1` and off
parameters `type=0x80, val=0`. The integration already implements these semantics.
The **Cloud Platform Service Interface**, section 4.5.8, delegates device-specific
control parameters to the attribute specification.

**The reviewed v2.32 attribute specification does not list BJ84**, although an
official product page is available. That page establishes the product's
four-circuit/eight-key design, but does not publish the `SL_SW_BJ84` identifier,
API port mapping, or command parameters. The integration's `P1-P8` mapping
is based on two locally discovered `SL_SW_BJ84_V1` panels reporting named channels
with types 128/129 and values 0/1. Protocol support remains based on these
observations rather than a BJ84-specific API specification. The official cloud
API documentation also does not specify the integration's local TCP framing;
that existing transport is reused without modification.

Unnamed `P9-P23` fields reported types 254/255 on those panels. Their meanings
have not been established, so they are not exposed or written. A channel name
alone does not establish whether it controls a relay, a scene, or another
configured action. No pulse, curtain, or scene behavior is inferred from names.

Synthetic tests cover entity creation and filtering, distinct panel identities,
state dispatch, local model normalization, and P8 command packet routing.
Physical command effects and automatic reset behavior require device testing.
This includes checking how configured logical channels trigger actions and
whether they remain on or reset after activation. No physical commands were
sent during integration validation.
